# Sharebuff threat model — one page (v4, `--tiny` default)

**Parameters.** locator 25 bits (public) · key 40 bits (`--tiny`, small text) · 128 (`--short`, automatic for files and text > 4 KiB) · 256 (`--full`) · PIN 50.3 bits (4 dictionary words from 6,134; `--pin-words 6` → 75, 16 random chars → 80) · scrypt N=2¹⁶ r=8 = 64 MiB, ≈0.1 s per core-evaluation for a well-equipped attacker (≈1 s in a browser) · 10 counted wrong claims then burn · cooldown min(2ⁿ, 300 s) after the n-th miss, uncounted 429s inside it · 7-day TTL · one-shot, tombstoned before the ciphertext is returned.

**Three things protect a secret.** The *code* (locator+key, in the link or typed), the *PIN* (other channel), and the *ciphertext* (server, until claimed). Confidentiality needs an attacker to obtain **code + PIN + ciphertext**. The table gives the cost of getting whatever they lack.

| # | Scenario — attacker has | Must still get | Work | Time (tiny) | Outcome | Mitigation |
|---|---|---|---|---|---|---|
| 1 | **Leaked link** (code), online | PIN, 50.3 bits, via the claim API | 10 counted guesses; P(success) = 10/2⁵⁰·³ ≈ 1 in 140 trillion | 810 s of cooldowns + ~10 s scrypt ≈ **14 min to burn** the secret | Availability only: attacker can *burn* it; cannot read it | Sender re-posts; PIN never travels with the link |
| 2 | **Nothing**, online — burn strangers' secrets | A live locator (25 bits) | 33.5 M / L requests to find one of L live secrets (404 vs 403 reveals liveness); no scrypt needed for garbage proofs | L=100: ≈335 k requests ≈ **6 min at 1 k req/s** to find one, 14 min to burn each, parallelizable | Availability only | Per-IP limits at the edge: 10 creates / 30 claims per minute (429 before any Durable Object is touched); `rate_limited` and `secret_burned` alerts |
| 3 | **Server breach** (locator, ciphertext, verifier), no link | key + PIN jointly, 90.3 bits, offline | 2⁹⁰·³ ≈ 1.5 × 10²⁷ scrypt evaluations; no key-only oracle exists | 10⁵ cores: **≈ 50 trillion years** | None. Only unclaimed secrets (≤ 7 days) are even present; claimed ones are tombstones | Retrieve promptly; secrets self-destruct |
| 4 | **Server breach + leaked link** | PIN only, 50.3 bits, offline | 2⁵⁰·³ ≈ 1.4 × 10¹⁵ scrypt evaluations = **4.4 M core-years** | 1 000 cores: ≈ 4 400 years · 100 000 cores: ≈ **44 years** — *identical for every tier*; only the PIN is left | Disclosure, if the secret was still unclaimed at breach time | `--pin-words 6` (75 bits) or a 16-char PIN (80 bits) → beyond reach; never send link and PIN on the same channel |
| 4b | **Server breach + leaked PIN** (no link) | key only, offline | tiny (small text): 2⁴⁰ ≈ 1.1 × 10¹² scrypt = 3 500 core-years · short/full: 2¹²⁸ / 2²⁵⁶ | tiny: 100 000 cores ≈ **13 days**, a 1 000-GPU farm ≈ 2 days · short/full: infeasible | Disclosure of *small text* shared with the tiny code, if unclaimed at breach time | Automatic tier: files and text > 4 KiB always get the 128-bit key; use `--short`/`--full` for sensitive snippets; retrieve promptly |
| 5 | **Quantum computer + breach** (Grover) | key + PIN | √ of #3: 2⁴⁵ *coherent* scrypt iterations (tiny), 2⁸⁹ (short), 2¹⁵³ (full); with the link too: 2²⁵ for any tier | No credible hardware timeline for running a 64 MiB memory-hard function in superposition; formally `--full` meets the 128-bit PQ bar, tiny/short do not | None in practice; on paper tiny is below the bar | `--full` for archival-grade material; longer PIN; no asymmetric crypto anywhere for Shor to attack |
| 6 | **Compromised origin** (Cloudflare account, deploy pipeline, edge) | — | Serve altered page JS that exfiltrates the typed code and PIN | **Next retrieval** | Disclosure of secrets retrieved after the compromise | 2FA + signed commits on the deploy path; self-hosted `sharebuff-server` for high-trust use; CSP blocks third-party scripts but cannot police first-party |
| 7 | **Recipient endpoint** (clipboard managers, download folder, browser history holding the fragment, shoulder-surfing a 13-char code) | PIN, if only the code was observed | — | Immediate, local | Code alone → scenario 1. History entries of claimed secrets are dead links (tombstoned) | Separate channels; clear clipboard after use |
| 8 | **Sender endpoint** (CLI: terminal scrollback shows code, PIN and a 40-char preview; browser Share tab: link + PIN on screen, plaintext in the page until posted) | — | — | Immediate, local | Both factors visible together on the sender's screen | Clear scrollback / close the tab; the page wipes the plaintext after posting |
| 9 | **Network MITM / recording** | Break TLS 1.3 (+HSTS; hybrid X25519+ML-KEM on Cloudflare) | Even then: payload is AES-256 ciphertext; the claim proof is one-shot and reveals nothing about K_enc | — | None | — |
| 10 | **Race / replay** | — | Concurrent valid claims | — | Exactly one winner; tombstone written before response | — |

**Accepted trade-offs.** The client-side scrypt is not verified by the server (an attacker can post raw proofs); online pacing comes from the per-secret cooldown/burn and the per-IP limits, not from proof-of-work. From recognizable corporate egress (SWG ASN, proxy-stamped headers, modern browser over HTTP/1.1, `X-Sharebuff-Policy` header) the **server refuses to create secrets** and the page removes the Share tab; patching the page or using curl changes nothing. It is a network control, not device DLP — a hotspot or another paste site bypasses it. `404`≠`403` leaks whether a locator is live (needed for usable errors; enables #2). A holder of the full link can always burn a secret (#1) — fail-closed by design. The origin (#6) is trusted, as in every browser-delivered end-to-end-encrypted app.

**Verdict on `--tiny`.** With the PIN at 50 bits, breach + leaked link (#4) is out of practical reach for every tier. Tiny's real exposure is **#4b — breach + leaked PIN**: its 40-bit key falls to a GPU farm in days. That is why tiny is now reserved for short clipboard text and files/large payloads get the 128-bit key automatically; for sensitive snippets use `--short`, and `--full` for the paper-only quantum case (#5).
