# Sharebuff threat model — one page (v4, `--tiny` default)

**Parameters.** locator 25 bits (public) · key 40 bits (`--tiny`; 128 `--short`; 256 `--full`) · PIN 30 bits (6 chars; `--pin-len` raises it) · scrypt N=2¹⁶ r=8 = 64 MiB, ≈0.1 s per core-evaluation for a well-equipped attacker (≈1 s in a browser) · 10 counted wrong claims then burn · cooldown min(2ⁿ, 300 s) after the n-th miss, uncounted 429s inside it · 7-day TTL · one-shot, tombstoned before the ciphertext is returned.

**Three things protect a secret.** The *code* (locator+key, in the link or typed), the *PIN* (other channel), and the *ciphertext* (server, until claimed). Confidentiality needs an attacker to obtain **code + PIN + ciphertext**. The table gives the cost of getting whatever they lack.

| # | Scenario — attacker has | Must still get | Work | Time (tiny) | Outcome | Mitigation |
|---|---|---|---|---|---|---|
| 1 | **Leaked link** (code), online | PIN, 30 bits, via the claim API | 10 counted guesses; P(success) = 10/2³⁰ ≈ 1 in 107 million | 810 s of cooldowns + ~10 s scrypt ≈ **14 min to burn** the secret | Availability only: attacker can *burn* it; cannot read it | Sender re-posts; PIN never travels with the link |
| 2 | **Nothing**, online — burn strangers' secrets | A live locator (25 bits) | 33.5 M / L requests to find one of L live secrets (404 vs 403 reveals liveness); no scrypt needed for garbage proofs | L=100: ≈335 k requests ≈ **6 min at 1 k req/s** to find one, 14 min to burn each, parallelizable | Availability only | Per-IP rate limit at the edge (Cloudflare rate-limiting rule) — recommended next step |
| 3 | **Server breach** (locator, ciphertext, verifier), no link | key + PIN jointly, 70 bits, offline | 2⁷⁰ ≈ 1.2 × 10²¹ scrypt evaluations; no key-only oracle exists | 10⁵ cores: **≈ 37 million years**; single core: 3.7 × 10¹² years | None. Only unclaimed secrets (≤ 7 days) are even present; claimed ones are tombstones | Retrieve promptly; secrets self-destruct |
| 4 | **Server breach + leaked link** | PIN only, 30 bits, offline | 2³⁰ ≈ 1.07 × 10⁹ scrypt evaluations = **3.4 core-years** | 1 000 cores: ≈ 1.2 days · 100 000 cores: ≈ **18 min** — *identical for every tier*; only the PIN is left | Disclosure, if the secret was still unclaimed at breach time | `--pin-len 8` → ×1 024 (100 k cores: 13 days); `--pin-len 10` → ×10⁶; never send link and PIN on the same channel |
| 5 | **Quantum computer + breach** (Grover) | key + PIN | √ of #3: 2³⁵ *coherent* scrypt iterations (tiny), 2⁷⁹ (short), 2¹⁴³ (full); with the link too: 2¹⁵ for any tier | No credible hardware timeline for running a 64 MiB memory-hard function in superposition; formally `--full` meets the 128-bit PQ bar, tiny/short do not | None in practice; on paper tiny is below the bar | `--full` for archival-grade material; longer PIN; no asymmetric crypto anywhere for Shor to attack |
| 6 | **Compromised origin** (Cloudflare account, deploy pipeline, edge) | — | Serve altered page JS that exfiltrates the typed code and PIN | **Next retrieval** | Disclosure of secrets retrieved after the compromise | 2FA + signed commits on the deploy path; self-hosted `sharebuff-server` for high-trust use; CSP blocks third-party scripts but cannot police first-party |
| 7 | **Recipient endpoint** (clipboard managers, download folder, browser history holding the fragment, shoulder-surfing a 13-char code) | PIN, if only the code was observed | — | Immediate, local | Code alone → scenario 1. History entries of claimed secrets are dead links (tombstoned) | Separate channels; clear clipboard after use |
| 8 | **Sender endpoint** (terminal scrollback shows code, PIN and a 40-char preview) | — | — | Immediate, local | Both factors visible together on the sender's screen | Clear scrollback; the preview is deliberately 40 chars |
| 9 | **Network MITM / recording** | Break TLS 1.3 (+HSTS; hybrid X25519+ML-KEM on Cloudflare) | Even then: payload is AES-256 ciphertext; the claim proof is one-shot and reveals nothing about K_enc | — | None | — |
| 10 | **Race / replay** | — | Concurrent valid claims | — | Exactly one winner; tombstone written before response | — |

**Accepted trade-offs.** `404`≠`403` leaks whether a locator is live (needed for usable errors; enables #2). A holder of the full link can always burn a secret (#1) — fail-closed by design. The origin (#6) is trusted, as in every browser-delivered end-to-end-encrypted app.

**Verdict on `--tiny`.** Confidentiality holds in every scenario except **breach + leaked link (#4)**, where the remaining barrier is the PIN — and that is true of *all* tiers, so tiny costs nothing there. Tiny's only unique exposure is the paper-only quantum case (#5). If #4 is in your threat model, raise `--pin-len`; if #5 is, use `--full`.
